# V1.1 PN-04 Profile Request Retention

Profile correction, removal, and identity-claim requests contain contact and source details. The database assigns a 90-day expiry and `profiles.pn04_purge_expired(uuid)` deletes expired rows only after confirming the supplied membership is an active staff member of the selected active platform organization. The function is executable by `perspective_runtime`; anonymous `perspective_public` callers cannot execute it.

The authenticated worker is `POST /api/v1/internal/pn/worker/purge-expired-requests`. It requires a bearer token of at least 32 characters, a platform organization UUID, and an active platform staff membership UUID. The route sets the tenant context, uses the restricted runtime role, and returns only a count. Database error details and request content are not returned.

## Scheduler configuration

The repository workflow `.github/workflows/pn04-profile-request-retention.yml` runs daily at 03:17 UTC. It is deliberately disabled unless the repository Actions variable `PN04_RETENTION_ENABLED` is exactly `true`. The workflow also supports manual dispatch after it has been enabled.

Before enabling it for a released V1.1 deployment, configure:

- **Hostinger application secrets:** `PERSPECTIVE_PN04_RETENTION_TOKEN`, `PERSPECTIVE_PN04_RETENTION_ACTOR_ID`, and `PERSPECTIVE_PN04_RETENTION_ORGANIZATION_ID`.
- **GitHub Actions repository secret:** `PERSPECTIVE_PN04_RETENTION_TOKEN`, using the same random token.
- **GitHub Actions repository variable:** `PERSPECTIVE_INTERNAL_BASE_URL`, set to the HTTPS origin of the released application, with no trailing slash or path.
- **GitHub Actions repository variable:** `PN04_RETENTION_ENABLED=true`, set only after the application deployment and environment configuration have been verified.

`PERSPECTIVE_PN04_RETENTION_ACTOR_ID` must be an `iam.organization_memberships.id`, not a user account ID. It must belong to the platform organization selected by `PERSPECTIVE_PN04_RETENTION_ORGANIZATION_ID`, and remain active as `STAFF`. The app validates these values again in the database. Do not commit token values or place them in workflow YAML.

When rotating the token, update the Hostinger secret and GitHub Actions secret together, then trigger a manual workflow run and verify a successful response before relying on the next scheduled invocation. Keep the workflow disabled until the route is deployed and the exact production target has been verified. A successful run returning `{"deleted":0}` is valid when there are no expired requests; it does not prove end-to-end deletion, so retain the local database test as separate evidence.
